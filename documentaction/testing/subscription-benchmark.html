Subscriptions

Benchmark page for WebSocket subscription fan-out, client scaling and per-key notification distribution.

Source files: servers/subscriptions/subServer_benchmark_test.go and servers/subscriptions/subServer.go.

What It Measures

BenchmarkSubscriptionServer opens real WebSocket clients against HandleWS, subscribes them to one or more keys, then measures how fast NotifySubscribers(...) can fan out updates.

This benchmark measures the subscription server path itself, not the full save -> db write -> async notify path. The regular save flow dispatches notifications in a goroutine, so database writes/s should be measured separately.

Basic Commands

# default scenarios: clients=10,100 and keys=1,10
go test ./servers/subscriptions -run '^$' -bench BenchmarkSubscriptionServer -benchmem

# fixed-iteration run for easier comparisons between machines
go test ./servers/subscriptions -run '^$' -bench BenchmarkSubscriptionServer -benchmem -benchtime=100x -count=1

# one small local smoke run
$env:TSU_SUB_BENCH_CLIENTS='4'
$env:TSU_SUB_BENCH_KEYS='2'
$env:TSU_SUB_BENCH_KEYS_PER_CLIENT='1'
$env:TSU_SUB_BENCH_PARALLELISM='1'
$env:TSU_SUB_BENCH_PAYLOAD_BYTES='64'
go test ./servers/subscriptions -run '^$' -bench BenchmarkSubscriptionServer -benchtime=20x -count=1

Scaling Scenarios

# more clients and more keys
$env:TSU_SUB_BENCH_CLIENTS='100,500,1000'
$env:TSU_SUB_BENCH_KEYS='10,100'
$env:TSU_SUB_BENCH_KEYS_PER_CLIENT='1'
$env:TSU_SUB_BENCH_PARALLELISM='4'
$env:TSU_SUB_BENCH_PAYLOAD_BYTES='256'
go test ./servers/subscriptions -run '^$' -bench BenchmarkSubscriptionServer -benchmem -benchtime=100x -count=1

# heavier fan-out per client: every client listens to multiple keys
$env:TSU_SUB_BENCH_CLIENTS='200'
$env:TSU_SUB_BENCH_KEYS='50'
$env:TSU_SUB_BENCH_KEYS_PER_CLIENT='5'
$env:TSU_SUB_BENCH_PARALLELISM='4'
$env:TSU_SUB_BENCH_PAYLOAD_BYTES='512'
go test ./servers/subscriptions -run '^$' -bench BenchmarkSubscriptionServer -benchmem -benchtime=100x -count=1
VariableMeaning
TSU_SUB_BENCH_CLIENTSComma-separated client counts. Each value becomes a benchmark scenario.
TSU_SUB_BENCH_KEYSComma-separated key counts. Each value is combined with every client count.
TSU_SUB_BENCH_KEYS_PER_CLIENTHow many keys each client subscribes to.
TSU_SUB_BENCH_PARALLELISMParallel send factor passed to b.SetParallelism(...).
TSU_SUB_BENCH_PAYLOAD_BYTESPayload size of each synthetic update body.

Benchmark Metrics

MetricMeaning
writes/sCalls per second to NotifySubscribers(...). One write targets one key.
notifications/sTotal WebSocket messages delivered per second across all subscribed clients.
notifs/writeAverage fan-out of one write. Example: value 50 means every update reaches 50 clients on average.
clientsConfigured number of connected WebSocket clients.
keysConfigured number of benchmark keys.
active_keysKeys that actually ended up with at least one subscriber in that scenario.
keys/clientNumber of subscribed keys per client.
subscriptionsTotal active subscriptions, usually clients * keys/client.
subs/keyAverage subscribers per active key.
payload_BBytes in each benchmark payload.
Time/opAverage wall-clock time of one benchmark write operation.
Memory/opHeap bytes allocated per benchmark write.
Allocs/opHeap allocation count per benchmark write.

How To Read Results

If This ChangesInterpretation
writes/s drops while notifs/write stays flatThe server is getting slower per update even though fan-out stayed similar. Compare payload size and parallelism.
notifications/s rises but writes/s fallsYou are pushing broader fan-out per update. Total delivered traffic increased, but each write became heavier.
notifs/write rises sharplyEach key has more subscribers. This is expected when you increase clients or reduce the key count.
active_keys is below keysSome configured keys received no subscribers. This can happen when clients * keys/client is smaller than the total key count.

Example Output

BenchmarkSubscriptionServer/clients=100/keys=10/keys_per_client=1/parallel=4/payload=256B-16
    100   41800 ns/op   23923 writes/s   239230 notifications/s   10.000 notifs/write   3450 B/op   36 allocs/op

Interpretation: one benchmark write targets one key, and each key has about 10 subscribers on average, so notifications/s is about 10x higher than writes/s.
