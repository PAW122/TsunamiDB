Subscriptions

Subscriptions use private HTTP endpoints to mint auth keys and a public WebSocket endpoint to stream real-time key events.

Load-test commands and metric definitions for the WebSocket subscription fan-out path are documented on Testing & Benchmarks / Subscriptions.

Flow

  1. Your trusted backend calls POST /subscriptions/enable with a list of keys.
  2. TsunamiDB returns a one-time auth_key valid for about 60 seconds.
  3. Your client connects to ws://localhost:5845/sub and sends {"auth_key":"..."}.
  4. The socket receives subscribed, then update/delete events for the authorized keys.

Practical Example: Online Users

A common use case for SubscriptionServer is a live Online Users field in a dashboard, admin panel, or landing page.

  1. Your backend stores the current online-user count under one key, for example online-users in table stats.
  2. When a client opens a screen that should show the live counter, your trusted backend enables a subscription for online-users and returns the one-time auth_key.
  3. The frontend opens ws://localhost:5845/sub, sends the auth key once, and waits for events.
  4. Whenever your application writes a new value for online-users, TsunamiDB pushes an updated event automatically to all subscribed clients.
  5. The UI refreshes the field immediately, so users see the new count without polling the API.

This is usually the best fit for values that change often and should be reflected on screen in real time.

Practical Example: Live Document Edits

For document editing, use /patch/{table}/{key} instead of saving the whole document on each keystroke. TsunamiDB applies the patch to the stored value, then streams a patched event with only the operations that changed.

{
  "event": "patched",
  "key": "doc-1",
  "patch": [
    { "offset": 120, "insert": "hello" }
  ]
}

Clients should load the full value once through /read, subscribe to the document key, then apply incoming patched events locally. Use updated as a full-value refresh event and patched as an incremental edit event.

Example Communication Scheme

Recommended subscription communication pattern:

POST /subscriptions/enable

curl -X POST http://localhost:5844/subscriptions/enable \
  -H "Content-Type: application/json" \
  --data '{"keys":["user-1","event-feed"]}'

Response:

{"auth_key":"uuid-value"}

POST /subscriptions/disable

Removes active subscribers for one key and sends them an unsubscribed event.

curl -X POST http://localhost:5844/subscriptions/disable \
  -H "Content-Type: application/json" \
  --data '{"key":"user-1"}'

WS ws://localhost:5845/sub

{"auth_key":"uuid-value"}

Successful response:

{"event":"subscribed","keys":["user-1","event-feed"]}
