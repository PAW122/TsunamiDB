HTTP Key-Value

Basic operations save, read and delete bytes in a table under a key.

Data saved usingsave is saved in plain text.

POST /save/{table}/{key}

Reads the request body as bytes, stores it in table, and associates it with key. Re-saving the same key replaces metadata and marks the old span for defragmentation.

InputValue
BodyAny bytes. Use --data-binary for curl.
Header modeOptional. Set save_nested_json to extract nested JSON payloads.
Success bodysave
 
curl -X POST http://localhost:5844/save/users/user-1 \
  -H "Content-Type: application/octet-stream" \
  --data-binary "Hello, TsunamiDB"

POST /patch/{table}/{key}

Applies one or more byte-range patch operations to an existing value. TsunamiDB reads the current value, applies the operations in request order, saves the merged value, and emits a patched subscription event containing only the patch operations.

FieldMeaning
base_revRequired when revision mode is current or history. Must match the stored revision before TsunamiDB accepts the patch.
ops[].offsetZero-based byte offset in the current value at the moment that operation is applied.
ops[].deleteOptional number of bytes to remove starting at offset.
ops[].insertOptional UTF-8/string bytes to insert at offset.
ops[].insert_b64Optional base64 bytes for binary inserts. Do not combine with insert in the same operation.
Success body{"status":"patched","key":"...","size":123,"base_rev":1,"rev":2}. Revision fields are present only for versioned keys.
 
curl -X POST http://localhost:5844/patch/users/user-1 \
  -H "Content-Type: application/json" \
  --data '{"ops":[{"offset":5,"insert":","},{"offset":7,"delete":9,"insert":"TsuDB"}]}'

Use /patch for live editing workflows where clients should send small changes instead of repeatedly saving the whole document. If the key does not exist, the endpoint returns 404; invalid offsets, delete lengths or patch bodies return 400.

When revision tracking is enabled and base_rev does not match the current stored revision, the endpoint returns 409 with {"error":"revision_conflict","base_rev":...,"current_rev":...}. The client should fetch missing patches or reload the full value.

Revision Tracking

Revision tracking is optional per key. It is a storage policy, not a WebSocket-only setting, so it keeps working while all clients are disconnected.

ModeBehavior
offDefault. No revision checks and no patch history.
currentStores the current rev. Patch requests must include matching base_rev.
historyStores current rev and retained patch records for reconnect catch-up.
 
curl -X POST http://localhost:5844/revision/docs/doc-1 \
  -H "Content-Type: application/json" \
  --data '{"mode":"history"}'

curl http://localhost:5844/revision/docs/doc-1

curl -X POST http://localhost:5844/patch/docs/doc-1 \
  -H "Content-Type: application/json" \
  --data '{"base_rev":0,"ops":[{"offset":0,"insert":"Hello"}]}'

curl "http://localhost:5844/revision/docs/doc-1/patches?from_rev=0"

Full /save operations on a versioned key increment rev. In history mode, a full save resets the patch history start, so older clients should perform a full resync instead of replaying stale patches.

Patch history is bounded by TSU_REVISION_HISTORY_MAX_PATCHES. The default is 1000 retained patch records per key; set it to 0 or a negative value to disable trimming. If a client asks for from_rev older than history_from_rev, the server returns 409 and the client should reload the full value.

GET /read_with_revision/{table}/{key}

Reads the stored value and revision state under the same per-key lock used by /patch. Use this endpoint when a client needs a consistent initial snapshot before applying streamed patch events.

FieldMeaning
data_b64Base64-encoded value bytes, safe for binary documents.
revCurrent revision for the key.
revision_modeoff, current or history.
history_from_revFirst revision from which retained history can be replayed, present when non-zero.
 
curl http://localhost:5844/read_with_revision/docs/doc-1

GET /read/{table}/{key}

Returns the decoded user bytes. If the key is not local, TsunamiDB asks connected P2P peers.

curl http://localhost:5844/read/users/user-1

P2P Table-Aware Reads

With the new network manager flow, peers exchange a catalog of available tables. That means node A can answer a user read even when the requested table exists on node B, as long as both nodes are connected in the P2P network.

AspectDetails
SelectionThe request prefers peers that advertise the requested table.
FallbackIf the catalog is still warming up, the read can fall back to querying a broader peer set.
EncryptionSet TSUNAMI_NETWORK_SECRET to encrypt node-to-node traffic.

GET /free/{table}/{key}

Removes the key from the map and marks the stored data range as free. If the value has nested JSON chunks, linked nested chunks are also cleaned up.

curl http://localhost:5844/free/users/user-1

Nested JSON Mode

Nested mode is for large JSON documents where selected fields should be stored as separate chunks. Send JSON to /save with header mode: save_nested_json. Any string value starting with @ becomes a nested value.

{
  "profile": {
    "name": "edgar",
    "bio": "@{\"links\":[\"https://example.com\",\"https://github.com\"]}"
  },
  "logs": "@[{\"ts\":1730000000,\"event\":\"LOGIN\"}]"
}
curl -X POST http://localhost:5844/save/users/user-2 \
  -H "Content-Type: application/json" \
  -H "mode: save_nested_json" \
  --data-binary @payload.json

Reading Nested Values

HeaderBehavior
noneReturns base JSON with unresolved nested pointers replaced by "*".
read_nestedExpands only listed paths and keeps other nested values as "*".
read_only_nestedReturns an object containing only the selected nested paths.

Header names are matched case-insensitively by Go's HTTP server. Paths can be space-separated, comma-separated, or a JSON array.

curl http://localhost:5844/read/users/user-2 -H "read_nested: profile.bio logs"
curl http://localhost:5844/read/users/user-2 -H "read_only_nested: [\"profile.bio\"]"
